# Milestone 2 — Integrated Core System

Target workflow: **Customer → Restaurant → Menu → Cart → Checkout → Order**
Suggested tag: `m2-integrated-system`

## 1. How M2 is organized (read this first)

The `m2-contracts` PR creates every M2 file **once**, as placeholders, so feature work only
ever touches files you own. It deliberately contains almost no logic: schemas, error types,
auth, persistence, and checkout are left as `TODO` questions for the team to decide.

Already wired up (don't re-add these in feature PRs):
- every M2 router is registered in `app/main.py`
- every repository/service has a dependency provider in `app/api/deps.py`
- every layer has an isolated test fixture in `tests/conftest.py`
- any unimplemented method raises `NotImplementedError`, which the API returns as **501**

**Before anyone implements:** answer the TODOs in the shared files below *together*,
in the contracts PR review or one short meeting. Everyone builds on them.

| Shared file | Decide together |
|---|---|
| `app/schemas/*_schema.py` | Every request/response field |
| `app/core/exceptions.py` | Which errors exist and their HTTP status codes |
| `app/main.py` | How domain errors become HTTP responses |
| `app/api/deps.py` | How `get_current_user` / `require_roles` work (Person A leads) |
| `app/repositories/json_file_store.py` | How files are loaded/saved safely and how IDs are made |
| `app/services/cart_service.py` (bottom TODO) | What checkout needs from the cart (Persons B + C) |

After that, changes to shared files go in a small separate PR the whole team agrees on.

constructor). Never open another subsystem's JSON file or edit its files.

## 3. Questions to answer before coding

- Which M2 business rules (spec section 4) does each service enforce? Draw who calls whom.
- In what order do the checkout steps run, and why does the order matter?
- Which data must be *copied* into an order rather than referenced, and why?
- Where is "a deactivated customer can't …" enforced, so it exists in exactly one place?
- What does Person D need to add to restaurants/menus so the cart can use them?

## 4. Merge order

1. `m2-contracts` (placeholders, plus the shared decisions above)
2. In parallel: A (customers + auth), B (cart), D (restaurant/menu changes the cart needs)
3. C (checkout + orders), written in parallel but merged after B
4. C's integration test: register → sign in → browse → add to cart → checkout → order

## 5. Day-to-day rules

- One issue → one branch → one small PR. Aim to merge within 2–3 days.
- `git fetch && git merge origin/main` into your branch daily and before opening a PR; run `pytest`.
- Don't rename/move files or reformat whole files in a feature PR.
- Shared docs (`README.md`, `PROVENANCE.md`, this file): append to your own section only.
- Don't commit data files changed by running the app; only commit deliberate seed data.
- The PR author resolves conflicts, reruns tests, and re-requests review. Nobody approves their own PR.

## 6. Testing without waiting on auth

`tests/conftest.py` has a `login_as` fixture that overrides `get_current_user`, so cart and
order tests can pretend a user is signed in. Update it once `CurrentUser` has its fields.
`tests/test_m2_contracts.py` holds a checklist of skipped tests; replace each with a real one.
